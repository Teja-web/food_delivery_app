# Requirements Document Generator

Generate a comprehensive **Requirements Specification Document** for the current project. This document consolidates all approved requirements into a single, well-structured artifact suitable for stakeholder review, audit trails, and downstream design work.

## When to Use

- At the end of the REQUIREMENTS phase, after all requirements have been approved.
- When stakeholders need a consolidated view of project requirements.
- When the team needs a baseline document for design and development planning.

## Instructions

### Step 1 — Gather Context

Call `get_my_context` to retrieve the current project details, then list approved requirement-like plans:

```
invoke: get_requirements { kind: "story", status: "approved" }
```

If the project uses `feature` plans for requirements instead of stories, call `get_requirements { kind: "feature", status: "approved" }` too. Combine both sets.

### Step 2 — Generate the Document

Produce a Markdown document with the following structure. Every section is mandatory; use "N/A" if information is not available.

```markdown
# Requirements Specification Document

**Project:** {Project Name}
**Version:** 1.0
**Status:** Approved
**Date:** {YYYY-MM-DD}

## 1. Executive Summary

{2–3 paragraph overview: business problem, proposed solution, key stakeholders.}

## 2. Scope

### 2.1 In Scope
{Bulleted list derived from approved requirements.}

### 2.2 Out of Scope
{Explicitly excluded items; "N/A" if none.}

## 3. Functional Requirements

For each approved requirement, render:

### 3.{n} {Requirement Title}

- **ID:** {plan.id or slug}
- **Priority:** {p0 | p1 | p2 | p3}
- **Description:** {requirement.summary or body intro}
- **Acceptance Criteria:**
  {bullet list — extract from body if present, else "See requirement body"}
- **Source:** plan/{slug}

## 4. Non-Functional Requirements

{Performance, security, accessibility, observability — pull from any approved
`adr` plans or from requirement bodies tagged "nfr". "N/A" if none.}

## 5. Constraints & Assumptions

{From requirement bodies and ADRs. "N/A" if none.}

## 6. Dependencies

{External systems, integrations, prerequisite work. "N/A" if none.}

## 7. Glossary

{Terms used in the document. "N/A" if none.}

## 8. Traceability

| Req ID | Title | Source |
|---|---|---|
| ... | ... | plan/{slug} |
```

### Step 3 — File the Document

Call `upsert_plan` to land the document as a reviewable plan:

```
invoke: upsert_plan {
  kind: "epic",
  slug: "requirements-spec-{project-slug}",
  title: "Requirements Specification — {Project Name}",
  summary: "Consolidated approved requirements as of {YYYY-MM-DD}.",
  body: "{generated markdown}",
  changeNote: "Regenerated by requirements-document skill"
}
```

The first call creates a draft plan. Subsequent calls with the same slug append a `plan_revisions` row — safe to re-run as requirements evolve.

## Quality Checklist

- [ ] All approved requirements appear in section 3
- [ ] Each requirement has ID, priority, description, acceptance criteria
- [ ] Traceability table is complete
- [ ] No "TBD" or placeholder text remains
- [ ] Document is renderable as `.docx` via the Phase-2 plan export endpoint
