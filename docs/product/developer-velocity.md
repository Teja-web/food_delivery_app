# Developer Velocity — The Other Side of Govern. Verify. Trust.

Mirror of [positioning.md](positioning.md). Positioning is buyer-facing (CTO, CISO, VP Eng). This is **developer-facing**. Same operating model, different reader, different outcomes.

## The contract

> Governance pays developers back.

Most governance products are net-negative to developer productivity. Coznt is not, by design. Each pillar of the operating model earns developers something concrete that they can feel inside their editor on a Tuesday afternoon.

If a coznt feature ever makes a developer's day slower without a named payback, the feature is wrong.

## The mirror operating model

| Buyer pillar | Developer outcome |
|---|---|
| **Govern** what AI can do | **Earn autonomy** — less approval-wait, fewer humans in the loop |
| **Verify** what AI produces | **Ship clean** — fewer reverts, less post-merge firefighting |
| **Trust** what can be proven | **Review faster** — provenance lets you triage AI code in seconds, not minutes |

The buyer reads "we govern AI agents." The developer reads "your good work compounds into less friction." Same mechanism. Different surface.

## Pillar 1 — Govern → Earn autonomy

**The promise.** A skill that has demonstrated clean outcomes in your project graduates from intern → junior → senior → principal autonomy. Higher autonomy = fewer approval steps = faster merges. Good work directly purchases less ceremony.

**Why this is a developer feature, not a control feature.** Autonomy is *earned per-project*, not granted. It moves with evidence (`skill_outcomes`), not with politics. A developer on a well-disciplined project ships with materially less overhead than one on a chaotic project — and the difference is visible.

**Surfaces:**
- **Personal autonomy dashboard.** "Your projects average autonomy: senior. One project at junior — here's why." With a path to senior.
- **Approval-wait leverage.** "Your PR has been waiting 18h on Sarah." Today devs refresh Slack; coznt makes the wait first-class and ping-able from the IDE.
- **MCP verbs in the editor.** `coznt plan`, `coznt approve`, `coznt autonomy-status` — no context switch to a dashboard for the common verbs.
- **Skill outcome streaks.** Visual reinforcement: ten clean PRs in a row → autonomy promotion candidate.

**Anti-pattern to avoid.** Showing autonomy levels without showing the path to next level. Without the path, it reads as judgment.

## Pillar 2 — Verify → Ship clean

**The promise.** Pre-merge verification is faster than post-merge firefighting. The verification debt score and gate signal tell you what to fix *before* you push, not after a reviewer finds it.

**Why this is a developer feature, not a quality feature.** Most "quality" tools surface problems after submission. Coznt's deterministic assessors (`pr_merge`, `pr_revert`, `pr_abandon`, `deploy_clean`, `deploy_incident`) make the cost of a bad merge legible *before* the merge happens. A dev who sees "this PR will raise project verification debt by 14%" can rework before pushing.

**Surfaces:**
- **Verification debt as a blocker map.** Not a score — a list. "Three things between your PR and a clean merge: (1) coverage gate, (2) one open approval, (3) one rule violation."
- **PR-time projected delta.** "Current project debt: 42. This PR projected delta: −7." Negative delta = you're paying down debt. Positive delta = you should explain why.
- **Spec-first authoring.** If `spec` is structured (not markdown), AI generates closer to intent first try. Less iteration, less rework. The spec Plan kind is a velocity feature for developers, not a documentation chore.
- **Pre-flight gate run.** `coznt verify` in the editor: run all gates locally before push. Costs nothing if you already know it'll pass; saves a CI round-trip when it won't.

**Anti-pattern to avoid.** Surfacing verification debt as a number without an actionable breakdown. A score that can't be moved is a guilt mechanism, not a velocity tool.

## Pillar 3 — Trust → Review faster

**The promise.** Reviewing AI-generated code is cognitively harder than reviewing human code. Eye-tracking research shows reviewers context-switch more, delete-and-rewrite more, take longer. Coznt provenance annotations let reviewers triage in seconds.

**Why this is a developer feature, not an audit feature.** Reviewer velocity *is* team velocity. Every minute saved on a code review is a minute the team ships faster. Provenance is not bureaucracy; it is the cognitive offload that makes AI-assisted PRs reviewable at the speed AI generates them.

**Surfaces:**
- **PR provenance overlay.** "Lines 42–78 generated by junior-autonomy `change-risk-classifier` from prompt `[hash]`. Lines 80–95 hand-written." Reviewer reads the overlay first and knows where to spend attention.
- **Reviewer triage prefix.** A PR opens with: "This PR touches the payments service. Two relevant rules. One open security gate." The reviewer is oriented before reading a line.
- **Source-of-record one-click.** Every claim coznt makes (verification debt, autonomy level, gate status) links to the underlying ledger row. Trust is mechanical, not vibes — and that mechanicality is what makes it fast.
- **Reviewer-load fairness.** Per-team approval-latency rollups make silent senior overload visible. A junior who notices "Sarah has 14 open approvals" can self-assign and unblock the team without escalation.

**Anti-pattern to avoid.** Trust UI that requires a dashboard visit. If trust isn't legible inside the PR review surface or the IDE, it doesn't reach the developer.

## What "super-productivity for developers" looks like, concretely

Borrowing the personal-productivity lessons from [super-productivity](https://github.com/super-productivity/super-productivity), translated to coznt's governed-SDLC frame:

| Super-productivity pattern | Coznt developer-velocity equivalent |
|---|---|
| Short syntax (`task @tag #project +2h`) | MCP verbs (`coznt plan @auth #payments →approval:eng-lead`) |
| Keyboard shortcuts | Editor-native verbs, no dashboard hops |
| Auto-import issues from tracker | Mirror Jira/Linear into Plans; status writes route back via adapter |
| Time tracking with project tagging | Time-in-phase derived from phase transitions (no manual tracking) |
| Pomodoro / break reminders (flow protection) | Approval-wait leverage + gate-status pings (unblock flow, not interrupt it) |
| Worklog export | DX rollups that fall out of the audit ledger automatically |
| Plugin API for customization | Skills + MCP server for custom validators and verbs |

The unifying principle: **fast tools that meet developers where they already are**. Super-productivity's lesson was that personal productivity tools win on speed and ergonomics. The same is true for governance tools — they win on speed and ergonomics or they don't get adopted.

## Developer-velocity invariants

These are the contracts coznt commits to. If a feature breaks one, the feature is wrong.

1. **No verb requires a dashboard.** Every common developer action has an MCP/IDE surface.
2. **Every blocker is actionable.** A status that says "blocked" without saying *by what, on whom, and how to unblock* is a defect.
3. **Autonomy is earned, not granted.** Evidence drives the ladder. Politics doesn't.
4. **Provenance is a default, not a setting.** AI-generated regions are annotated automatically; reviewers don't opt in.
5. **Source-of-record links work.** Every claim on screen is one click from the row that proves it.
6. **Surfacing without overhead.** If coznt's UI imposes more time-cost than the friction it removes, it's net-negative and gets reworked.

## What this is NOT

- **Not a productivity tracker.** Coznt does not measure individual developers' hours or LOC. The unit of measurement is plan / PR / outcome, not human.
- **Not a competitor to the IDE.** Cursor / Copilot / Claude Code own the editor turn. Coznt provides the governance and provenance layer those tools call into.
- **Not a "gamification" play.** Streaks and autonomy paths are surfaces on top of real evidence. The ladder is load-bearing in the schema; it's not a UI sticker.
- **Not optional.** Developer velocity is a first-class outcome of the operating model. PM trade-offs that quietly degrade developer payback are violations of the contract above.

## Open questions

1. **Personal vs. project dashboard.** Should developers have a personal coznt view (my PRs, my approvals, my autonomy across projects) or stay project-scoped? Suggest personal view; it is the developer-side mirror of the portfolio audit.
2. **Editor surface depth.** How much of the developer-velocity surface ships via MCP only vs. native IDE extension (VS Code, JetBrains)? MCP is sufficient for Claude Code / Cursor; JetBrains likely needs a dedicated plugin.
3. **Approval-latency leverage UX.** Ping-able wait is powerful but adjacent to manager-style nagging. How is it framed so it stays developer-leverage and not surveillance? Suggest the developer initiates the ping; coznt never pings on their behalf.
4. **Velocity surfaces in the "PR check" comment.** How much developer-side information belongs in the GitHub/GitLab PR check vs. the coznt UI? Suggest: blocker map and projected debt delta in the PR check; everything deeper lives in coznt.
